# Uptime Kuma (homelab instance)

Uptime Kuma runs **in-cluster** (`monitoring` namespace) and is reconciled from Git. It is not
configured through a config file — the database inside the PVC is the only state, so the
`uptime-kuma-sync` CronJob is the bridge between `kubernetes-manifests/` and the live instance.

## Where everything lives

| Thing | Location |
| :--- | :--- |
| Workload, PVC, Service, probes | `kubernetes-manifests/monitoring/uptime-kuma.yaml` |
| Desired monitors (SOURCE OF TRUTH) | `kubernetes-manifests/monitoring/uptime-kuma-monitors.yaml` |
| Hourly reconciler (CronJob + inline `sync.py`) | `kubernetes-manifests/monitoring/uptime-kuma-sync.yaml` |
| PDB (`maxUnavailable: 0`) | `kubernetes-manifests/monitoring/availability.yaml` |
| Admin credentials | Secret `monitoring/uptime-kuma-credentials`, generated by kustomize `secretGenerator` from the **gitignored** `kubernetes-manifests/monitoring/uptime-kuma-credentials.env` |
| Longhorn backup push token | Secret `monitoring/longhorn-backup-push-token` (created after first sync, see `uptime-kuma-monitors.yaml`) |

Apply changes with `kubectl apply -k ./kubernetes-manifests` (or `-k ./kubernetes-manifests/monitoring`).

## Access

- **Tailnet (preferred, from Mac/phone):** `http://uptime-kuma` — `302` to `/dashboard` when signed out is healthy.
- **In-cluster:** `http://uptime-kuma.monitoring.svc.cluster.local` (Service 80 → containerPort 3001).
- Port 3001 speaks HTTP only; there is **no `/health` endpoint** in 2.x (SPA catch-all), which is why
  every probe is a `tcpSocket` check on 3001, not an HTTP GET.

## Monitor model (read this before editing monitors)

- 40 monitors at the time of writing: 17 `http`, 22 `port`, 1 `push`.
- The sync is **additive only**: adding a monitor to `monitors.yaml` creates it; **removing one does not
  delete it** remotely — delete strays in the UI. Drift on listed monitors *is* corrected
  (`type`, `url`, `hostname`, `port`, `interval`, `maxretries`).
- Cross-namespace targets must use FQDN service DNS (`<svc>.<ns>.svc.cluster.local`); short names do
  not resolve from the `monitoring` namespace.
- `server-236` / `server-252` node monitors are deliberately absent (permanently `NotReady`); the
  `registry-docker-tcp` monitor covers `.236` liveness instead.
- `longhorn-backup-daily` is a **push** monitor fed by the `backup-daily-check` CronJob; it goes DOWN if
  no Completed Longhorn backup younger than 26 h is pushed.

### v2 compatibility trap

`uptime-kuma-api 1.2.1` targets the 1.x schema and omits the NOT NULL `conditions` column, so
`add_monitor()` fails on 2.x. `sync.py` therefore posts the payload directly
(`_build_monitor_data` → `conditions=[]` → `_call("add", data)`). The pip pin to `1.2.1` and this
bypass must be revisited together — changing one without the other breaks monitor creation.

## Run the sync by hand

```bash
kubectl -n monitoring create job --from=cronjob/uptime-kuma-sync uk-sync-manual
kubectl -n monitoring logs -f job/uk-sync-manual | tail -3   # expect "sync done: created=… updated=… unchanged=…"
```

Healthy steady state is `created=0 updated=0 unchanged=40` (interval `17 * * * *`). A hang past
`activeDeadlineSeconds: 300` usually means the Kuma pod is down or the credentials Secret is missing.

## Query monitors from a Mac

The global agent skill `uptime-kuma` (installed at `~/.agents/skills/uptime-kuma`, from ClawHub
`@msarheed/uptime-kuma`) wraps the same API:

```bash
pip install uptime-kuma-api
export UPTIME_KUMA_URL=http://uptime-kuma/        # tailnet hostname works
export UPTIME_KUMA_USERNAME=<from secret>
export UPTIME_KUMA_PASSWORD=<from secret>
python ~/.agents/skills/uptime-kuma/scripts/kuma.py status
python ~/.agents/skills/uptime-kuma/scripts/kuma.py list --json | jq '.[].name'
```

Read the password without printing it:
`kubectl -n monitoring get secret uptime-kuma-credentials -o jsonpath='{.data.password}' | base64 -d`

## Gotchas

- `strategy: Recreate` is required — the PVC is `ReadWriteOnce`; two pods at once would corrupt MariaDB.
- `startupProbe` (6 s × 30) exists so a cold MariaDB start is not SIGKILLed by liveness; the TCP socket
  never depends on monitored services, so down targets can never restart Kuma.
- The image is pinned to an explicit `2.5.x` tag (currently `2.5.11`); bump the manifest and verify the
  pod restarts cleanly rather than relying on a floating `2` tag.
- Registry `192.168.0.236:5000` is on `server-236`; when that host is off, no new image pulls succeed
  (Kuma's image comes from Docker Hub, so it is unaffected).

## Verification

```bash
kubectl -n monitoring get deploy uptime-kuma -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
kubectl -n monitoring get pods -l app=uptime-kuma
kubectl -n monitoring get cronjob uptime-kuma-sync
curl -s -o /dev/null -w '%{http_code}\n' http://uptime-kuma/     # 302 = up
```
