# K3s upkeep plan — findings from the 2026-11-21 recovery

**Baseline after this session:** 10/10 nodes `Ready`, `/readyz` and `/readyz/etcd` `ok`,
three embedded-etcd members in one lineage, 24/24 Longhorn volumes healthy, 180 Running
pods, 0 Pending/ContainerCreating/CrashLoop.

**Topology decision:** keep the 3-member embedded-etcd control plane. "Minimal mode" means
`nuc` + `server-236` + `server-252` + one worker (`kubernetes5`). `nuc` alone cannot form
quorum (2 of 3 voters required), so a single-master NUC is not a legal target.

## 2. Recurring failure modes to detect automatically

1. **Etcd lineage fork.** Any control-plane member whose journal shows `cluster ID mismatch`
   or whose `k3s.service.env` is empty/missing `K3S_URL`. Check this before any archive/rejoin.
2. **Orphaned Longhorn attachment tickets.** For each `volumeattachments.longhorn.io`, compare
   `spec.attachmentTickets[].id` with Kubernetes `VolumeAttachment` objects and live pods.
   A `csi-attacher` ticket whose node no longer hosts the consumer is stale.
3. **Shared-RWO co-location.** Workloads that mount the same RWO PVC must land on one node.
4. **Node capability constraints.** CPU-sensitive images must avoid `kubernetes8-debian`.
5. **Power state.** `kubernetes8-debian` needs WoL; its MAC is in the port map.
6. **Stale health data.** Node lists and backup fields in diagnostics must match the live CRD.

## 3. Upkeep cadence

### After every power cycle (mandatory gate)
- `kubectl get nodes` — all expected nodes `Ready`; no unexpected `SchedulingDisabled`.
- `kubectl get --raw /readyz/etcd` — `ok`; three `started` members, one cluster ID.
- On each master: `stat -c '%s' /etc/systemd/system/k3s.service.env` and `grep K3S_URL`.
- `kubectl get volumes.longhorn.io -A` — no `faulted`/`degraded`; detached volumes only if
  explicitly baselined.
- `kubectl get pods -A` — no `Pending`/`ContainerCreating`/`CrashLoopBackOff`.

### Daily (cheap, scriptable)
- Run the fixed health script and review only its recommendations section.
- Check backup freshness with `status.backupCreatedAt`, threshold 26 h.
- List pods stuck > 30 min and their events.

### Weekly
- Audit Longhorn attachment tickets against live Kubernetes VolumeAttachments.
- Verify at least one restored backup can be read (not just that the CR says `Completed`).
- Review node disk usage and Longhorn replica scheduling failures.

## 4. Script changes to make (acceptance criteria)

- **`Start-K3sHomelab.ps1`**
  - Preflight etcd env/cluster-ID before any drain or uncordon.
  - WoL for `kubernetes8-debian` using inventory MAC when that node is a target.
  - Detect orphaned Longhorn tickets and report them before storage repair.
  - Minimal mode must be a named, tested target: `nuc` + 2 masters + `kubernetes5`.
  - Dry-run output must match what the real run would do.

- **`shutdown_homelab.ps1`**
  - Never leave one of the three etcd members powered on while the other two reboot.
  - Power off all three masters together, or keep all three on.
  - Write a restart manifest (what was powered off, when, with what method) so bring-back is auditable.
  - Full shutdown and minimal shutdown converge on the same start script.

- **`Stop-K3sHomelab-Minimal.ps1`**
  - Leave exactly the survivor set from `homelab-nodes.json`: `nuc`, `server-236`,
    `server-252`, `kubernetes5`.

- **`Repair-ContainerCreating-Pods.ps1`**
  - Match PV name, not PVC claim name, when locating volume attachments.
  - Remove stale Longhorn `csi-attacher` tickets instead of patching `status.ownerID`.
  - Keep force-delete of the stuck pod as the last step.

- **`Test-K3sClusterHealth.ps1`**
  - Use live `homelab-nodes.json` inventory; drop `kubernetes7`.
  - Use `SuryenduB` only for `server-236`.
  - Backup freshness from `status.backupCreatedAt`.

## 5. Acceptance test for the target state

1. Run `Stop-K3sHomelab-Minimal.ps1 -DryRun`, then the real minimal shutdown.
2. Verify only `nuc`, `server-236`, `server-252`, `kubernetes5` are on the LAN.
3. Run `Start-K3sHomelab.ps1 -DryRun`, then the real start.
4. Gate: 4 nodes `Ready`, `/readyz/etcd` `ok`, 3 etcd members started in one lineage,
   all Longhorn volumes healthy, no Pending/ContainerCreating pods, key apps Running.
5. Repeat full-cluster start (all 10 nodes) and re-run the same gate.

Do not leave one etcd member running while the other two reboot. That single rule explains
both the 2026-10-17 and 2026-11-15/21 lineage forks.

## 7. Live test result — FAILED (2026-11-21)

The minimal shutdown itself worked: all six target workers were cordoned, drained and
powered off; the three etcd members and `kubernetes5` stayed up; a restart manifest was
written to `WindowsLab/logs/shutdown-manifest.latest.json`. One node (`kubernetes8-debian`)
needed password-based SSH because its key auth is rejected; the script now records that as
`ssh-failed` in the manifest.

The **start gate failed on storage, not on etcd**:
- `/readyz` and `/readyz/etcd` stayed `ok`; all three etcd members remained in one lineage.
- With only `kubernetes5` as a Longhorn storage node, 3-replica volumes had nowhere to
  place replicas. Result: 9 attached/degraded, 13 detached/faulted, 2 detached/unknown.
- 28+ application/system pods stayed Pending or CrashLooping; the start script exited 2
  with `-FailOnDegraded`. It correctly did **not** restore faulted volumes from backup
  because `-Force` was not supplied, so no writes were discarded.

**Conclusion:** "3 masters + 1 worker" is quorum-safe but **not storage-safe** with the
current Longhorn layout. WoL also only wakes `kubernetes3` and `kubernetes8-debian`; the
other four workers need physical power-on.

Owner decision after the failed test: **implement Option A** (3 Longhorn workers in minimal),
a minimal workload profile, and WoL pre-enablement, then re-test.

Implemented after all nodes were physically powered back on:
- Survivor set changed to `nuc, server-236, server-252, kubernetes1, kubernetes3, kubernetes5`
  (three etcd members + three Longhorn storage nodes).
- `homelab-nodes.json` gained `wolIface` per worker and a `minimalProfile.scaleDown` list of
  16 non-essential Deployments.
- `Stop-K3sHomelab-Minimal.ps1` scales those Deployments to 0, records their original replica
  counts in the restart manifest, enables NIC WoL (`ethtool -s <iface> wol g`) before poweroff,
  and uses `sshpass` so `kubernetes8-debian` (which rejects SSH keys) can be shut down.
  `kubernetes2`'s NIC had `Wake-on: d`; it was changed to `g`.
- `Start-K3sHomelab.ps1 -Minimal` restores the scaled-down Deployments from the manifest.

Re-test of the new minimal cycle is pending completion of the full-cluster recovery that
followed the failed test.

## 8. Warning for the current live state

The cluster is **left in the minimal state by owner decision**: only `nuc`, `server-236`,
`server-252`, `kubernetes3` and `kubernetes5` are up; the other five workers are powered off.
Longhorn has 13 faulted and 9 degraded volumes. Before resuming normal service, power on
the missing workers and re-run `Start-K3sHomelab.ps1`; do not supply `-Force` for faulted
volume restore unless you have verified the newest backup is an acceptable recovery point.
